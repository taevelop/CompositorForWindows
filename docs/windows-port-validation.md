# Windows 포트 구현 및 검증 — 2026-09-22

## 구현 범위

계획의 기술 검증과 핵심 편집 MVP를 저장소 루트에 구현했다. C#/.NET 10, WPF, SkiaSharp 4.152.1, MSVC x64 네이티브 DLL을 사용한다. 최초 클론한 macOS 소스는 `macOS/`에 보존하고, Windows 빌드는 `native/kernels/`에 독립 복사한 C/H 소스를 사용한다.

PNG/JPEG 입출력, 기본 레이어 편집과 7개 합성 모드, 이동·크기·회전·뒤집기, 브러시·지우개, Undo/Redo, 기본 픽셀 레이어 `.comp` 저장·열기를 제공한다. UI 모델은 Apple 및 WPF 이미지 객체를 소유하지 않고, 256×256 premultiplied RGBA8 불변 타일을 공유한다.

마스크·그룹·조정·효과·PSD는 후속 단계다. RAW·AI·텍스트·자동 업데이트도 아직 제공하지 않는다. 해당 메타데이터가 포함된 프로젝트는 열기를 거부한다. [사용법과 정확한 제한](../README.md)을 참고한다.

## 검증 결과

- Release 솔루션 빌드: 경고 0, 오류 0.
- 자동 테스트 38개 통과: 네이티브 함수 실행, 타일 불변성, 경계 연결, 투명도·지우개·변환된 레이어 브러시, 입력 빈도 독립성, Undo/Redo, 합성 픽셀, 타일 보간 이음새, 프로젝트 왕복, 실패 복구, 미지원/손상 파일 거부, PNG/JPEG 내보내기, EXIF 8방향.
- 증분 화면 합성을 전체 새 렌더링과 픽셀 단위로 비교: 브러시·지우개·Undo·레이어 표시/삭제에서 일치.
- 숨김 WPF 창에서 브러시 → Undo/Redo → 속성 적용 → 이동 → 화면 캡처 → 종료 경로 검증.
- 자체 포함 `win-x64` 패키지 생성. 해당 실행 파일의 별도 숨김 실행에서도 네이티브 DLL 로딩과 편집 경로 통과.
- 실제 Mac에서 생성한 파일의 양방향 교환, 물리 포인터 입력 지연, 펜 압력, 다중 모니터 DPI, GPU, 대규모 레이어 스택은 미검증.

## 4K 브러시 측정

장비: Intel Core 5 210H, 논리 프로세서 12개, RAM 약 64GiB, Windows 11 build 26200, x64. Release 빌드, 4000×4000 문서, 800px 브러시, 경도 0%, 불투명도 100%, 1000×1000 화면 합성. 각 스트로크는 120회 입력이며 문서 안에서 진행한다.

다음은 `artifacts/benchmark-viewport.json`에 기록된 한 번의 실행 결과다. 모델 갱신, 증분 합성, offscreen 화면 복사를 포함하며 **WPF 표시나 input-to-photon 지연은 포함하지 않는다.** 원본 Mac 벤치마크와 경로·표시 조건이 다르므로 직접적인 성능 우열 비교는 하지 않는다.

| 레이어 | 스트로크 | 갱신 중앙값 | 갱신 p95 | 종료·히스토리·다음 합성 | 측정 시 working set |
|---|---:|---:|---:|---:|---:|
| 빈 레이어 | 1 | 10.16ms | 13.87ms | 7.04ms | 210MiB |
| 빈 레이어 | 2 | 10.22ms | 12.53ms | 2.43ms | 294MiB |
| 불투명 이미지 | 1 | 13.13ms | 18.05ms | 3.35ms | 620MiB |
| 불투명 이미지 | 2 | 13.22ms | 18.50ms | 1.79ms | 542MiB |

초기 내부 기준인 p95 33.3ms, 종료 100ms를 이 장비의 네 경우 모두 충족했다. 일정 프레임률이나 다른 장비 성능을 보장하지 않는다. 스트로크당 관리 힙 누적 할당량은 약 366–371MiB이며, 동시 상주 메모리와는 다르다. 장시간·다중 레이어 작업은 후속 최적화 대상이다.

초기 구현의 p95 61–80ms 병목을 다음 변경으로 개선했다.

1. 매 픽셀 해시 조회 대신 타일 행을 묶어서 복사.
2. 변경 없는 브러시 타일 재사용, 불필요한 이미지 복사 제거.
3. 이웃 픽셀을 포함한 타일 캐시 유지.
4. 브러시로 변경된 화면 영역만 다시 합성. 구조 변경·줌·이동에는 전체 화면을 갱신.

GPU 도입 전 CPU 구조 개선으로 초기 기준을 통과했으므로 현재 MVP는 CPU 렌더링을 유지한다. 고해상도 화면과 다층 문서에서 기준을 넘으면 같은 문서/편집 모델을 유지하면서 GPU 백엔드를 평가한다.

## 다시 검증하기

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File build.ps1 -Test -Benchmark -Publish
```

실행 파일: `artifacts/publish/Compositor.Windows.exe`. 전체 폴더가 필요하다. 빌드·측정·화면 캡처 산출물은 Git에서 제외한다. 외부 서비스 업로드와 자동 CI 등록은 수행하지 않았다.

## 폴더 분리 후 검증 — 2026-09-22

Windows 구현을 저장소 루트로 이동하고 최초 클론(`609dbea`)의 215개 파일을 `macOS/`에 보존했다. 줄바꿈 정규화를 적용한 Git blob 비교에서 원본과 모두 일치했다. Windows 전용 `native/kernels/`의 C/H 16개도 macOS 대응 파일과 SHA256이 일치한다.

새 루트에서 `build.ps1 -Test -Publish`를 실행하여 Release 빌드(경고 0, 오류 0), 테스트 38개, 숨김 WPF 스모크 테스트와 배포 폴더 생성을 통과했다. `artifacts/publish/Compositor.Windows.exe`의 별도 스모크 실행, 네이티브 DLL 및 라이선스 포함 여부도 확인했다. macOS 빌드는 이 Windows 환경에서 실행하지 않았다.
