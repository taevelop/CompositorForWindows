# Windows 실사용 안정화 검증

2026-09-22, 기준 커밋 `fea2315` 이후 로컬 변경. 마스크 구현 전 입력·문서 상태·복구 경로를 보강했다. macOS 소스는 수정하지 않았다.

## 수정 사항

- 이동 후 원위치 복귀, 동일 속성 적용에서 수정 표시와 불필요한 Undo가 생성되는 문제를 재현하고 수정했다. 변화 없는 편집은 기존 Redo도 유지한다.
- 저장 여부를 문서 참조 대신 수정 버전으로 관리한다. Undo/Redo가 저장된 버전으로 돌아오면 수정 표시가 해제되고, 새 분기는 별도 수정으로 취급한다. 저장 당시 이미지 전체를 별도 참조하지 않는다.
- Undo/Redo·취소가 선택 레이어를 복원하고, 삭제 직후 선택은 남은 레이어로 보정한다. 이력은 총 100단계와 현재 문서에 없는 고유 타일 256MiB를 모두 적용한다. 현재 이미지, 렌더 캐시, 실행 중 스트로크는 이 한도에 포함되지 않는다.
- 왼쪽 드래그 중 다른 버튼의 눌림/해제가 편집을 끝내지 않으며 휠 확대를 무시한다. Esc, 캡처 상실, 창 비활성화는 진행 중 편집을 되돌린다. Hand 이동도 Esc로 되돌린다.
- File → Open recovery copy…로 `.comp.recovery`를 읽기 전용 원본으로 열고 새 이름으로 저장한다. 열린 복구 문서는 처음부터 수정 상태다. 원본/복구 사본을 자동 삭제·교체하지 않는다.

## 자동 검증

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File build.ps1 -Test -Stability
powershell -NoProfile -ExecutionPolicy Bypass -File build.ps1 -Test -Publish
```

- 최종 Release 빌드: 경고 0개·오류 0개. self-contained win-x64 패키지 생성 후 배포 폴더의 실행 파일로 동일 WPF 검증을 통과했고 화면도 확인했다. 결과는 `artifacts/published-ui-smoke.checks.json`과 `artifacts/published-ui-smoke.png`에 남긴다.
- xUnit 51개: 기존 픽셀·타일·저장 검증, 수정 상태/선택/이력 한도/복구 회귀, 100%·150%·200% 상당 렌더 크기의 증분/전체 합성 픽셀 일치.
- 숨김 WPF 검증: 혼합 버튼, 드래그 중 휠, 비활성화, Esc, 캡처 상실 이벤트, pan 취소, PNG/JPEG 입력, 속성·브러시·지우개·Undo/Redo, 저장 후 세션 재설정/열기, 출력 일치, 손상·미지원 파일 거부, 복구 사본 저장, 종료 확인의 저장/버리기/취소 분기와 저장 실패.
- 종료 확인은 주입한 대화상자 응답으로 검사한다. 실제 취소 Close 및 최종 clean Close도 검사하지만, 저장/버리기 각 분기의 실제 창 종료는 모두 재현한 것이 아니다.
- 복구는 중단 후 디렉터리 상태를 재현한다. 실제 저장 프로세스 강제 종료·전원 중단은 실행하지 않았다.
- 결과 파일: `artifacts/ui-smoke.checks.json`, `artifacts/ui-smoke.png`, `artifacts/stability-benchmark.json`.

## 4K 다중 레이어 성능

Intel Core 5 210H, 논리 프로세서 12개, RAM 64GiB, Windows 빌드 26200, Release CPU 경로. 2026-09-22 08:41 UTC 측정.

서로 다른 4000×4000 소스 1/3/6개, 상단 레이어 불투명도 60% 및 Normal/Multiply 혼합, 최하단 레이어에 800px soft 브러시로 입력 120회 × 스트로크 2회. 1000×1000 Skia 뷰포트 합성을 포함한다. WPF 표시·실제 입력부터 화면 갱신까지의 지연은 제외한다. 아래 p95와 종료는 두 스트로크 중 큰 값이다.

| 레이어 | 최초 합성 | 갱신 p95 | 스트로크 종료 | 종료 시 working set 범위 |
|---|---:|---:|---:|---:|
| 1개 / 16MP | 90.6ms | 14.7ms | 5.3ms | 424–473MiB |
| 3개 / 48MP | 174.2ms | 23.3ms | 3.0ms | 917–918MiB |
| 6개 / 96MP | 349.1ms | 30.5ms | 4.0ms | 1301MiB |

모두 초기 갱신 p95 ≤33.3ms, 종료 ≤100ms 기준을 충족했다. 최초 합성은 별도 비용으로 남아 있으며, 6개 레이어는 갱신 기준에 여유가 크지 않다. 실제 창 크기·DPI·장비·부하에 따라 달라지므로 GPU 불필요를 뜻하지 않는다.

프로세스 최대 working set은 약 1303MiB였다. 이전 시나리오와 소스 생성 메모리를 포함한 프로세스 누적 최고치다. 스트로크당 관리 힙 누적 할당은 370–384MiB, 6개 레이어 두 번째 스트로크 후 강제 GC 보존 관리 메모리는 418MiB였다. 할당량과 동시 보존량은 다르다.

## 반복 편집과 메모리

1024×1024, 서로 다른 색의 800px 브러시 160회, 512×512 뷰포트, Undo/Redo 각 20회, 새 문서 열기를 측정했다.

| 시점 | Undo/Redo | 이력 전용 타일 | 강제 GC 후 관리 메모리 |
|---|---:|---:|---:|
| 40회 | 40/0 | 143MiB | 147MiB |
| 80회 | 69/0 | 253MiB | 257MiB |
| 120회 | 69/0 | 253.8MiB | 258MiB |
| 160회 | 69/0 | 253.3MiB | 258MiB |
| Undo 20회 | 49/20 | 253.3MiB | 258MiB |
| Redo 20회 | 69/0 | 253.3MiB | 258MiB |
| 새 문서 | 0/0 | 0MiB | 8.3MiB |

히스토리 commit p95는 0.47ms였다. 타일 보존량은 한도 내에서 제한됐다. 새 문서 후에도 OS working set은 약 839MiB로 즉시 초기값에 복귀하지 않았다. 힙 예약·네이티브 할당을 포함한 working set과 살아 있는 타일을 구분해야 하며, 이 측정만으로 장시간 메모리 누수가 없다고 단정하지 않는다.

## 남은 검증과 다음 작업
